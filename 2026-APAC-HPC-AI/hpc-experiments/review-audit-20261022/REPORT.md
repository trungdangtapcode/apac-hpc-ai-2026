# Static audit: CPU pair payloads (2026-10-22)

## Findings

**NUMA128 provenance has a concrete mismatch.** The inherited candidate `PREPARATION.json` lists `system/decomposeParDict` under `immutable_input_hashes` as `ee76e1b47f56d98d5552de3c60e75801f194249bea8f47c19a0ac2816a570829`, while the submitted pair's accepted candidate input records `a06220c71b3e9b61fe1fb73b2a5ee377fa15dd3fdf676433f35e62889afdaf29`. The field was actually changed to configure native Scotch domains `(8 16)` and weights `(1 0.1)`, but the inherited metadata leaves it marked immutable and omits it from `changed_text_files`.

The pair's `payload/accepted-inputs.json` and the NUMA preparation collection hash the actual candidate dictionary as `a06220c71b3e9b61fe1fb73b2a5ee377fa15dd3fdf676433f35e62889afdaf29`. Therefore this is a false inherited immutability claim and incomplete `changed_text_files` provenance, not evidence that the frozen submitted input changed after submission. Pair payload hashing and its runtime `verify-inputs.py` compare against the actual candidate hash. Preserve both frozen records; correct the record only in a dated follow-up if authorized. See `nscc-cpu-numa-scotch128-20261021/collected/25907688.pbs101/artifacts/scotch-N128-numa8x16/PREPARATION.json`, its `evidence-sha256.json`, and `nscc-cpu-scotch-numa-pair128-20261021/payload/accepted-inputs.json`.

**NUMA128 static acceptance is otherwise coherent, with a misleading legacy marker.** `review.py` insists on `CPU_HS_PAIR_PASS`, but verifies role-specific input hashes and reports default Scotch versus NUMA Scotch. The marker alone does not identify the methods; `STATUS.md` already documents this. Its placement gate checks 128 ranks, one host, distinct physical cores, and eight groups of 16 ranks each bound to distinct single NUMA nodes. This establishes pre-solve rank affinity/grouping for that probe. It does not measure page residency, later solver affinity changes, or actual traffic. The one ordered run remains vulnerable to order/cache/host effects; hardware counters, memory bandwidth, MPI waits, and power were not collected, as stated in the reviewer.

**The 256-rank payload is prepared, not executed.** `validation.json` explicitly says there is no deployment, submission, or native multi-node execution. Its inputs pin the 65,334,765-cell case, 256 ranks, two nodes, and 80 steps; the verifier checks method/rank/cell count and hashes every listed input. The placement probe requires two hosts with 128 ranks each, unique physical cores per host, and contiguous 128-rank blocks per host. This is a useful launch-time mapping check, but it runs once before either solve; it does not establish that each solver invocation retained the same mapping or that memory stayed local. Saved `PBS_NODEFILE` and rank records can support a post-run comparison.

The 256-rank solve validator checks all 80 steps, fixed solver iteration counts, finite force-coefficient values, a broad `0.3 < Cd < 0.6` sanity bound, and a finite positive native average. It does not itself validate native per-step timing sample count or independently reconcile the reported average to the 79 timed steps. A post-run reviewer should do that, retain max/tail/outliers, compare method-specific Cd and all fixed work, and inspect phase/resource evidence. Current payload has no runtime measurements to judge.

## Next hypothesis

After the existing matched two-node hierarchical/default-Scotch baseline and the three-cut preparation gates are reviewed, test whether node-aware Scotch `(2 128)` with synthetic weights `(1 0.1)` lowers cross-host cut faces enough to reduce 80-step wall time on two nodes, without unacceptable total interfaces, worst-rank interface load, cell imbalance, neighbor count, Cd change, or tail regression. Require the actual 128-rank host-block guard before interpreting graph cuts as cross-host. This is a conditional, matched comparison, not a forecast of a win.

The pinned public ASPIRE reference analysis supports the question but not a causal claim: four-node Scotch was faster than hierarchical in the nosrx reference (3.210833 versus 3.440401 s/step) while its graph had fewer total interfaces (2,927,022 versus 4,306,118), much higher max-neighbor count (66 versus 20), and slightly larger max cell imbalance (1.072% versus 0.002%). Standard four-node Scotch was slower than hierarchical (3.575991 versus 3.414517 s/step). Those public runs are organizer observations with configuration/transport differences; rank-to-node mapping was unavailable, so interface counts are not measured network traffic. Source: `reference-analysis-20261021/RESULTS.md` and `reference-results.json`.
