# Reverse-order 30-step partition screen

This derived bundle reverses the single-pair run order from parent job 2294099: zyx first, then xyz. It tests whether the apparent advantage of zyx persists when it runs first, while retaining the same initialized xyz and zyx source cases, numerical work per step, one-node 56-CPU allocation, 30 steps per arm, and 29 measured intervals per arm. The solver cap is 1,150 seconds per arm; the shared internal deadline is 2,580 seconds and the outer job timeout is 2,640 seconds. The runner checks at least 1,270 seconds remain before beginning each arm and again immediately before each solver start. This protects the second solver from clone and setup overhead.

The parent screen's means were 32.592668524 seconds per step for xyz and 23.811097072 seconds per step for zyx, an apparent 26.94% reduction for zyx in that xyz-then-zyx allocation. However, xyz had 29 measured intervals against a native recommendation of 82; zyx had a recommendation of 4. Those are native confidence recommendations, not proof of independence or a formal confidence interval. Reversing order addresses one source of temporal and thermal confounding; a single reverse-order pair remains too small to establish a general solver-time advantage. Inspect every interval, native warning, fixed iteration counts, Cd, process/resource logs, affinity, source snapshots, and clone checks. Do not describe the short screen as a full 150-step or scored result.

At admission, maximum allocation is 45 minutes on 56 CPUs (42 allocated CPU-hours). The shared Iris ledger remains `iris-scotch56-20261025/budget.json`; do not create a second ledger. The deployment/submission tool requires an independently reviewed passing `completed-2294099/review.json`, applies the existing uncertain-intent guard and Iris queue cap, and reserves only after checking the existing ledger. Preparation does not itself seal, deploy, submit, modify the budget, or create receipts.


The parent run also showed GNU time major faults of 398,390 for xyz versus 31,526 for zyx, and filesystem input counts of 373,832 versus 69,616, while reported CPU percentages were nearly equal (5,545% versus 5,547%). This pattern motivates checking whether execution order, filesystem state, or startup effects contributed to the apparent gain. These aggregate counters do not establish a cause. The reverse-order runner records bounded metadata snapshots from `/proc/meminfo`, `/proc/vmstat`, and optional `/proc/pressure/memory` immediately before and after each solver; unavailable files are recorded as errors. The snapshots are whole-node counters and do not measure hardware memory bandwidth or attribute all changes to the solver process. No cache flush or system tuning is performed.
