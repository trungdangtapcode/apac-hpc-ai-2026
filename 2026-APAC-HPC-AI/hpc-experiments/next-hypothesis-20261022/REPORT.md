# Next distinct Basic-tier CPU hypothesis (2026-10-22)

## Recommendation

Once shared CPU ownership is resolved and the already queued Scotch node/rank comparisons are complete, consider a same-allocation causal transport comparison at the official 4-node / 512-rank / 150-step point. Shared jobs already set `FI_OFI_RXM_USE_SRX=0`; our pipeline sets `FI_VERBS_PREFER_XRC=0` and otherwise inherits site-default SRX. The question is therefore whether SRX off adds value to the current XRC-off configuration, not whether SRX off is a new or previously untested tactic. Hold `FI_VERBS_PREFER_XRC=0` fixed and explicitly compare `FI_OFI_RXM_USE_SRX=1` (control) against `FI_OFI_RXM_USE_SRX=0` (candidate). This changes one runtime setting, leaves decomposition and physics unchanged, and is Basic work under Task Rules F1, which permits MPI parameters and runtime environment variables. The current local pair wrapper exports `FI_VERBS_PREFER_XRC=0` ([pair payload](../nscc-cpu-scotch-numa-pair128-20261021/payload/pair.pbs)). The site notes document both settings and runtime provider diagnostics ([Task Rules, F1](../upstream-20261021/sources/2.%20OpenFOAM%20HPC%20Task%20Rules.md), [pinned ASPIRE-2A Application Notes](https://github.com/hpcac/2026-APAC-HPC-AI/blob/b4df52907f5bbb9152ef6ae902c925fc79d54417/4.3%20OpenFOAM%20Application%20Notes%20-%20ASPIRE-2A.md), [pinned upstream log tree](https://github.com/hpcac/2026-APAC-HPC-AI/tree/b4df52907f5bbb9152ef6ae902c925fc79d54417/4.3-aspire2a-logs)).

## Evidence for this question

The recovered one-node Scotch-versus-NUMA pair is a clear reason to leave that branch closed: default Scotch averaged **13.880988 s/step**, the NUMA tree **14.358715 s/step** (+3.4416% slower), despite 10.6283% fewer logical cross-NUMA faces. No page-residency, MPI-wait, bandwidth, or cache telemetry was collected, so this does not support another NUMA-tree trial ([NUMA pair results](../nscc-cpu-scotch-numa-pair128-20261021/RESULTS.md)).

At 256 ranks, the native input graph screen found **99,591** cross-group faces for default Scotch and **127,359** for node-aware Scotch, with the node-aware tree also having 1.206860% maximum cell excess versus 1.127319% for default. The graph is not measured traffic, but it makes the existing default-Scotch baseline the cleaner transport control; the node-aware tree has no current graph advantage ([N256 results](../nscc-cpu-three-cuts256-20261021/RESULTS.md)).

The pinned ASPIRE-2A notes report that default verbs/ofi_rxm runs failed at MPI finalization with signal 7, while either `FI_VERBS_PREFER_XRC=0` or `FI_OFI_RXM_USE_SRX=0` fixed all three small MPI probes and the 2-node `simpleFoam` smoke tests with identical Cd. For 4-node Scotch, the official full-chain averages were 3.575991 s/step with defaults, 3.244753 with XRC disabled, and 3.210833 with SRX disabled. Three additional solver-only repeats per setting ranged **3.221–3.373** for XRC-off and **3.176–3.387** for SRX-off. These ranges overlap, so the cross-run difference does not establish an SRX speedup. The 4-node Cd remained identical across these transport variants. SRX-off with the site's default XRC preference emits a conflict warning and disables XRC; the proposed comparison explicitly keeps XRC-off in both arms and verifies the effective provider settings in captured runtime output ([pinned reference analysis](../reference-analysis-20261021/RESULTS.md), [pinned public ASPIRE notes](https://github.com/hpcac/2026-APAC-HPC-AI/blob/b4df52907f5bbb9152ef6ae902c925fc79d54417/4.3%20OpenFOAM%20Application%20Notes%20-%20ASPIRE-2A.md)).

This targets the scored endpoint and separates the two already documented transport configurations on the same node set. It does not assume the old organizer runs used identical nodes, order, or cache state. The result would estimate the paired runtime effect of SRX at fixed XRC-off; it would not establish a general transport or network bottleneck.

## Matched comparison and gates

Use one exclusive 4-node / 512-rank allocation to run two complete, otherwise identical Scotch chains sequentially on the same node set: one with `FI_VERBS_PREFER_XRC=0, FI_OFI_RXM_USE_SRX=1`, the other with `FI_VERBS_PREFER_XRC=0, FI_OFI_RXM_USE_SRX=0`. Randomize or pre-register the order. Regenerate/restore the same official case inputs for each arm, run every required preparation command, and use the unchanged v2512 double-precision build, fixed iteration counts, function objects and 150-step endpoint. Capture effective MPI provider/configuration, host/rank placement, all stage return codes, complete solver logs, per-step timing distribution, `coefficient.dat`, field seals, MaxRSS and allocation phase timings. Retain the full Cd series and report the final Cd against the official sanity values (~0.28–0.29 at 150 steps). Byte-identical coefficient files are a useful diagnostic expectation for a runtime-only change, but bit identity is not a Basic acceptance requirement; the official rule is a sanity check and publishes no universal ± tolerance. Report any output differences without inventing a stricter gate. Keep all outliers in Average.

Cost estimate from the pinned full-chain Scotch jobs: XRC-off job 25710711 used **148.20 SU**, about **17:22** at 512 cores and 1 SU/core-hour; SRX-off job 25710718 used **134.40 SU**, about **15:45**. Together that is **282.60 SU / 33:07** of historical allocation time. A single 40-minute, 512-core allocation would reserve at most **341.333 SU**, leaving **58.733 SU / 6:53** headroom over those two observed runtimes. That margin is a risk, since the paired chains could run longer; do not truncate the official work if setup or runtime threatens the cap. A reversed-order confirmation would require another 341.333-SU allocation. Current ledger commitment is 170.866667 SU, so this first allocation would bring the planning total to 512.2 SU, and a confirmation would bring it to 853.533 SU before the queued rank comparisons. Their full maxima and shared jobs must be included before considering either allocation. Current ownership is unresolved; this is a research proposal only, not a queue or spending instruction.

Stop without confirmation if SRX-off is not at least **3% faster** in the paired average, if either arm changes the prescribed numerical work or fails a runtime gate, or if the effective provider/configuration cannot be verified. Three percent is a proposed practical threshold relative to the noisy, overlapping public ranges, not an official scoring tolerance. A final-Cd difference must be reported and checked against the official sanity values; it is not automatically a failed Basic run under a fabricated identity tolerance. If the first pair clears the timing threshold, consider one reversed-order pair only if the complete project plan remains within the existing 1,000-SU ceiling and shared CPU capacity is confirmed. If the reversed pair does not preserve the gain, close the setting branch.

## Limits

The official reference runs are organizer measurements, not team submissions; transport variants were not randomized on the same allocated nodes, and solver-only repeats reused decompositions. Existing shared SRX-off jobs are evidence that this setting has already been tried; the proposed work is only a same-node paired comparison against the pipeline's SRX-default/XRC-off configuration. The reference analysis lacks synchronized per-rank MPI wait, fabric traffic, CPU-frequency, and network-counter telemetry. `FI_OFI_RXM_USE_SRX=0` changes message-receive behavior, but no retained evidence proves that SRX is the current solver bottleneck. A speed difference would establish an observed runtime effect only, not its mechanism. The proposed 4-node pair should therefore follow, rather than replace, the pending Basic rank/decomposition baselines.
