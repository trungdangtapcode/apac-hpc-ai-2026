# Offline balanced rank-placement screen

## Question and inputs

Can runtime rank placement put the unchanged default-Scotch 128-way partition into eight equal logical groups with fewer interface faces crossing groups? The immutable input is the [validated default-Scotch graph](../nscc-cpu-numa-scotch128-20261021/validated-graph-default_scotch.json), SHA-256 `db4e5c7697a7959433f485c9f51e4126b65cc660f2891afa3a1619c91148f79f`. Retained [placement evidence](../nscc-cpu-numa-scotch128-20261021/placement-analysis.json) maps contiguous blocks of 16 ranks to eight NUMA nodes on one earlier compute node; it does not prove CPU IDs or node topology for a future allocation.

The initial reproducible screen used seed 2026, 20 random balanced starts, and one million simulated-annealing swaps. Its original output is preserved unchanged as [screen-initial.json](screen-initial.json): 368,634 crossing faces, 3,024 fewer than baseline (0.813651%). Because all random starts were unseeded by a known good assignment, the bounded refinement also added deterministic steepest improving balanced swaps from (1) baseline `rank // 16`, (2) the preserved initial best, and (3) the current annealing best. Every round scans all cross-group rank pairs and picks the most negative exact delta, with rank IDs as deterministic tie breakers. It stops at a one-swap local optimum or the 29-second overall runtime limit. One hundred seeded arbitrary swaps also checked incremental deltas against full edge recomputation.

## Result and decision

The baseline `rank // 16` mapping has **371,658** cross-group faces. Steepest descent from the preserved/current best reaches **354,658**, a reduction of **17,000 faces (4.5740977%)**. The baseline start is already a one-swap local optimum; both best-mapping starts converge to the same candidate in two improving swaps, and all three descents completed their local-optimum scans. The full candidate mapping, group membership, group-major rank permutation, inverse slot map, objective trail and validation are in [screen.json](screen.json). The complete search took about **3.49 seconds** in the retained run on this host.

This is a material graph-objective improvement relative to the initial screen's sub-one-percent result, so retain it as a candidate for a later, budgeted runtime comparison rather than closing the branch. It is not evidence of solver speedup: graph face weights do not measure memory traffic, MPI waits, or solver critical path. No pages, traffic, or solver timing were measured. A logical group corresponds to physical NUMA only if a fresh runtime placement probe verifies that mapping on the allocated node.

The graph invariants remain 128 ranks, 1,549,377 interface faces, 42,141 maximum interface faces on one rank, and 35 maximum neighbors. The graph and processor folders remain unchanged. The search only assigns the existing rank IDs to eight equal-capacity logical groups.

## Conditional runtime path and limits

Do not submit a comparison until shared-job ownership, queue capacity, and budget caps are resolved. If authorized and feasible, compare one same-node default-Scotch pair at 128 ranks and 40 steps, maximum **29 minutes / 61.866667 SU** for the pair, only if the approved ceiling and combined queue cap allow it. Use the candidate mapping consistently for every mandatory parallel initialization stage and solver process in its arm; the control retains site-default rank placement. Probe actual rank-to-CPU affinity, distinct physical cores, and intended NUMA groups on the allocated node before expensive initialization. Map logical groups onto that node's discovered CPU sets; never carry CPU IDs over from the older placement sample. If documented launcher binding cannot implement and verify the mapping, do not run the pair.

Task Rules F1 allow runtime rank placement and affinity in Basic. This is a runtime rank-to-CPU binding test, not relabeling processor directories or custom decomposition. Exact runtime environment and deterministic input make bitwise output equality a useful diagnostic, but it is not asserted here as an official Basic acceptance requirement. A runtime result would still need the normal source, stage, fields, placement, and cost review. This offline screen consumes no cluster budget, changes no payload, and has not established any performance benefit.

## Binding readiness and stopping rule

A read-only login check of the deployed PALS 1.1.6 launcher confirms that its command-level `--cpu-bind list:<cpu>:<cpu>:...` syntax is documented in `pals-launch-interfaces.txt`. This help/version check launched no MPI ranks or allocation. `render_binding.py` converts logical groups to CPU IDs only from the supplied rank probe; it never launches MPI or changes affinity. The historical example is a qualification artifact, **not a binding list for a new job**. The renderer passed against retained 128-rank topology, and rejected duplicate CPUs, duplicate physical cores, a second host, ambiguous initial affinity and a changed baseline rank-block/NUMA grouping. Root independently recomputed both graph cuts and verified the preserved initial-result hash. Details are in qualification.json.

Any later runtime pair must generate a fresh binding on the allocated node, verify it with a second probe, and apply it to the entire initialization and solver arm. Do not reuse historical CPU IDs, relabel processor directories, or assume startup affinity proves solve-time migration or page residency. Keep effective transport identical between arms. Require all source, stage-return, numerical-work, timer, force and field-seal gates; retain every timestep. The offline search is heuristic and proves no global optimum.

Before any eventual submission, pre-register the pair order and a practical timing threshold: retain this candidate for a reversed-order confirmation only if its same-allocation native Average is at least 3% lower and all validity gates pass. Otherwise close this mapping unchanged. The 3% threshold is a research decision, not an official scoring or Basic quality tolerance. A reverse pair costs another maximum 61.866667 SU and requires its own fresh budget/capacity check. Current shared queue ownership/cost coordination remains unresolved; no job is submitted by these files.

The fresh baseline probe must map contiguous rank blocks of 16 to eight distinct NUMA groups. Otherwise the retained 371,658-face control objective does not describe that placement: fail before initialization and recompute the control graph objective instead of silently reusing it.
