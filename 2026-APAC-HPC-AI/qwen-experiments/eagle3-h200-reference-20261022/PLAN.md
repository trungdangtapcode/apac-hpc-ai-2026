# H200 target-only exact-token reference proposal

This is an unsubmitted, CPU-validated preparation draft for the first step of the native H200 EAGLE3 route. It is separate from `serving-tuning-10` and the frozen H100 EAGLE3 payload. It produces a fresh H200 target-only reference; it does not run EAGLE3, AIPerf, a diagnostic profile, or a ranked workload.

The source is `serving-tuning-10/s30-h200-observed-n64-full-candidate`, preserving the operational native Slurm SGLang setup. The draft retains two TP4 prefill workers using DeepGEMM with chunk size 8192 and one TP8 / EP8 decode worker using HPC-Ops, FlashInfer and MNNVL. It retains the supported heterogeneous-TP NIXL patch by its original bytes and expected SHA256. Each worker has bounded resource sampling and phase markers; Slurm binds worker CPUs to allocated cores. The source launcher uses `kv_cache_dtype=auto`; the draft requires each worker's startup log to explicitly confirm the observed BF16 KV allocation before traffic. The target remains the staged FP8 model. The exact target files and image must be verified by the reviewing agent before freeze; sizes alone are not identity evidence.

The input is the frozen `prepared-corpus.json` from the 21 October corpus repair. Its four cases have tokenized prompt lengths 22, 21, 22 and 4000. The native `/generate` client sends two greedy passes, seed 2026, `ignore_eos=true`, and 200 new tokens for every case. Each response must carry all 200 actual output logprob IDs, including token zero, the expected prompt token count and a `length` finish reason. The independent head checker replays all eight response records, verifies the frozen corpus hash and every request field, compares both passes and requires 1600 collected output IDs. It does not compare against H100 output or infer anything from decoded text.

Before traffic, the native launcher checks the exact three-row placement, all three worker endpoints, the central router, and rank-specific BF16 KV allocation records. Each TP4 prefill log must contain the actual allocation line for ranks 0–3; the TP8/EP8 decode log must contain it for ranks 0–7 with matching TP and EP tags. Generic TP text elsewhere cannot satisfy this gate. The CPU-validated semantic pair helper exercises each prefill/decode path, retains raw successful responses and receipts, and binds them to the endpoint-inventory hash and a fresh experiment identifier. The identifier is a random UUID for provenance, not authentication material; the helper uses a one-way digest as its 32-character receipt token. The client is gated on both helper exit status and the complete semantic marker.

One absolute budget begins with the Slurm job process: 600 seconds for setup and startup, 120 seconds for semantic pair warmup, 210 seconds for the client, 20 seconds for result checks and 40 seconds for teardown. A failure triggers at most 40 seconds of cleanup, capped at the planned `T0+990` teardown boundary; it does not wait idle until that boundary. The launcher fails closed at the `T0+1020` hard stop inside the 17-minute allocation. These are proposed ceilings, not evidence that H200 startup will fit. No per-worker readiness timer renews the startup allowance. The experiment ID, absolute client deadline and image path are explicitly passed through each relevant container invocation.

## Exact derivation changes

- Kept native `job.sbatch`, `worker.sh`, placement, model path, runtime image path, NIXL patch, NUMA CPU binding and sampler design as the operational base. Removed the AIPerf benchmark, load summary, output-smoke and profiler routes from this correctness payload.
- Replaced the inherited sweep topology with a target-reference flow: shared absolute deadline, exactly two TP4 prefill workers plus one TP8/EP8 decode worker, BF16 KV log gate, semantic pair warmup, eight `/generate` requests and independent head-result validation.
- Replaced the H100 token helper's platform and old-reference checks with an H200 target-only two-pass capture. It uses the same frozen corpus and token-ID validation semantics, records current target small-file hashes, weight file names/byte counts, and the container image path and available byte size. It explicitly marks full large-weight and image hashes as not collected; paths and sizes are review clues, not identity proof.
- Replaced the H100 checker with a self-contained H200 head-process gate. It rejects missing/incomplete output records, 199-token output, wrong prompts or generation settings, bad finish reasons, mismatched passes, stale corpus hashes and a false semantic result flag.
- Replaced the unvalidated topology warmup with the CPU-validated semantic helper and warm-topology runner. Raw success bodies and receipts are retained; failed HTTP and semantic bodies are retained in a bounded response log without request headers.
- Added `SOURCE_PROVENANCE.json`, the complete current `SOURCE_SHA256SUMS`, and `prepare.py`. The preparation command verifies source, corpus and bundle hashes; optional installation refuses an existing destination. The inherited source checksum file is retained under `NATIVE_SOURCE_SHA256SUMS`, not left under a stale valid-manifest name.

## Evidence and limits

`validate-cpu.py` checks shell dispatch, exact placement, phase ordering, absolute deadlines, semantic warmup receipt use and rank-specific BF16 parsing. A local HTTP server runs the actual token client's `main()` for successful and malformed responses; the independent head checker accepts the complete 1600-ID result and rejects 199/missing/duplicate/invalid IDs, wrong prompts or request settings, bad finish reasons, mismatched passes and a false pass flag. A fake-Slurm launcher fixture runs the actual shell launcher and proves a nonzero client exit makes the launcher fail promptly through cleanup. Python 3.9 AST and shell syntax checks also pass, as does the standalone semantic-helper CPU suite. These checks do not emulate a GPU, model startup, multi-node transport or actual endpoint responses.

Redacted per-role/rank KV geometry is **not collected**. Adding it safely requires a validated runtime observer interface; this proposal does not add transport hooks or inspect raw pointers/peer metadata. Actual current H200 model and image identity, scheduler state, NIXL runtime success, startup time, BF16 KV behavior and exact token output remain unverified until owner review and an authorized allocation. No correctness, performance, official accuracy or EAGLE3 gain claim follows from this draft.

## Root review gates before any freeze or submission

Verify the actual H200 target and image identities from the cluster's current bytes, inspect the complete payload diff and checksums, validate that the 600-second shared startup budget is plausible from retained startup evidence, and confirm that every intended runtime argument is accepted by the deployed image. Then review whether the startup logs provide adequate rank/role evidence. Only after the target-only result passes its independent semantic gate can a separate EAGLE3 candidate be prepared against this fresh reference. This draft itself submits nothing and changes no source payload or budget.
