# DP attention and EP feasibility review (2026-10-24)

## Decision

A decode worker with `tp_size=5`, `dp_size=5`, `--enable-dp-attention`, `--ep-size=5`, `moe_dp_size=1`, and two redundant experts is source-plausible for Qwen3-MoE's 128 logical routed experts. DP attention changes the effective attention TP to 1, while 128 + 2 physical expert slots gives 130 slots / EP 5 = 26 slots per EP rank. This resolves the two arithmetic constraints that make ordinary attention TP 5 and an unpadded EP 5 layout suspect.

This is a source-level lead, not runtime qualification. The local image's Qwen3-MoE path uses a 128-output router gate and allocates 128 + `ep_num_redundant_experts` physical expert slots. `ExpertLocationMetadata` appends the two extra slots as logical replicas. Runtime dispatch/weight loading must actually use that map for the selected quantization and MoE path. The exact DP-attention-to-EP token exchange, request-to-rank NIXL mapping, H200 collective path, and full-model memory fit have not been run or proved here.

The most attractive low-risk topology to qualify first is **P12/D4**, with both attention groups at TP4: P12 can be expressed as TP12 × DP3 with DP attention, yielding attention TP4; D4 can use ordinary TP4. If the Qwen3 checkpoint's KV-head count is four as expected, both roles satisfy the model's attention head partition checks and use the same attention TP geometry for NIXL. EP4 divides 128 without redundant experts. The exact scheduler rank placement and whether the chosen role flags preserve those groups still need a small launch preflight.

**P11/D5** is a second, higher-uncertainty candidate. DP attention can make effective attention TP1 on both roles, and EP5 + 2 physical replicas is arithmetically valid. It also creates different DP group counts across the two roles, and there is no local runtime evidence that Qwen3's native MHA NIXL path pairs those P/D rank topologies correctly. If the SM90 FlashInfer all-reduce fusion backend is retained, the pinned CLI allows MNNVL on SM90 single-node systems only; a 5-GPU D group could be placed on one H200 node, but the 11-GPU P worker cannot be one node. Use an explicitly supported P-side backend or hold this topology until group-level backend resolution is checked. Do not infer that MNNVL works across H200 nodes.

The public Team01 layout hint is only a motivation for checking this path. It does not establish Team01's private implementation, exact flags, or score.

## Qualification plan before any full serving attempt

1. **CPU source-shaped gate:** use a minimal resolved-argument fixture (or source-level pure calculation, without importing CUDA runtime) to record per-role `tp_size`, `dp_size`, `enable_dp_attention`, `attn_tp_size`, `ep_size`, `moe_dp_size`, `moe_tp_size`, A2A backend, MoE runner and all-rank group membership. Assert P12/D4 gives attention TP4 on both sides and that P12 EP4 × MoE-DP3 and D4 EP4 × MoE-DP1 satisfy the source validators. Separately assert D5 EP5 has 130 physical experts, 128 logical IDs, and 26 physical slots per EP rank.
2. **CPU expert-map gate:** build the pinned trivial 128+2 expert map with the actual Qwen config shape; prove the two appended physical IDs map to valid logical IDs, each expert's logical-to-physical map is nonempty, ranks own exactly 26 slots for EP5, and the selected dispatcher maps each routed ID to one valid physical copy without duplicate contribution. Keep this as a structural fixture only; it cannot prove FP8 weight bytes or MoE math.
3. **One-H200 kernel smoke, only if the source-format gate passes:** on the pinned image, use a tiny synthetic FP8 MoE tensor with the checkpoint's exact quantization/block metadata and BF16 input to call the `hpc_ops` runner. Record selected quant method, block shapes/scales, activation path, output against a high precision reference, kernel availability and peak allocated memory. This does not qualify multi-rank EP, NIXL, model accuracy, or MNNVL.
4. **Smallest multi-GPU role preflight:** before a score run, launch the chosen P/D role geometry only long enough to collect actual server args, per-rank group IDs, effective attention TP and KV-head counts, expert-map summaries, backend-resolution logs, FP8 MoE runner eligibility, startup peak memory and a single controlled request's native NIXL completion. Run P12/D4 first if configuration permits; test P11/D5 only if the P/D system-DP mapping is explicit and the H200 collective selection is valid.

Do not authorize a full benchmark from source feasibility alone. Stop if any rank disagrees on resolved geometry, if the H200 multi-node all-reduce is resolved to MNNVL, if 130-to-128 expert mapping is not visible and rank-consistent, if actual MoE quant metadata is outside `hpc_ops` support, if the selected backend allocates 26 local experts inconsistently, if native NIXL reports mismatched layer/head lengths or lacks a deterministic P/D rank map, or if startup memory leaves inadequate measured KV/request capacity. A one-GPU runner smoke cannot clear those multi-GPU blockers.
