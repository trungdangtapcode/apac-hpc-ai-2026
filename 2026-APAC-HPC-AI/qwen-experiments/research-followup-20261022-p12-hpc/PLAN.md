# H200 P12/D4 HPC-Ops short interaction screen

## Question and prior evidence

The scored H200 runs 24962, 24964, and 25365 use two TP4 DeepGEMM/chunk8192 prefill workers and one TP8/EP8 HPC-Ops decode worker. New phase-aligned evidence from full N60 job 24964 shows that all 22 requests classified bad in the score begin in the first 16.991–35.088 ms of profiling; no later scored requests are bad. This timing is an association, not a demonstrated cause. The control also sampled decode running batches around 40–52, with GPU activity near 100% on decode and above 90% on prefills. These sparse samples do not prove a bottleneck.

The old P12-TP4/D4-TP4/EP4 topology was exercised in jobs 22273 and 22416 under the older auto-MoE stack. Job 22273 scored 742.33 good output tokens/s at 100% SLA for sweep N16, then 905.91 at 70.62% for N32, 751.15 at 48.19% for N40, and 272.46 at 15.00% for N48. Job 22416 confirmed N16 at 828.11 and 100% SLA. Those runs did not test the current H200 configuration at N60. They are a substantial warning that this split may lose, not a reason to repeat the old experiment.

The missing interaction is the current native stack combined with a P12/D4 resource split: three TP4 DeepGEMM/chunk8192 prefills and one TP4/EP4 HPC-Ops decode. It adds prefill capacity while halving decode GPU capacity. A short matched N60 pair can determine whether this narrow hypothesis merits any full-score followup. It cannot establish that the initial errors were caused by prefill capacity.

## Proposed pair

Both drafts derive from the immutable `serving-tuning-10/s21-dg8192-hpc-n60-control` source. They use H200, the same official FP8 model, native BF16 KV, NIXL and the existing heterogeneous-TP descriptor patch, DeepGEMM prefill with chunk8192, HPC-Ops decode, MNNVL, FlashInfer decode attention, dense decode graphs 1–64, round-robin routing, the same resource sampler, and N60 closed-loop 4000/200 input/output settings. Both use a 20-second warmup, 40-second scored window, and 30-second grace period. This is an unranked screen, not the full 60/120/30 local benchmark and not an official score.

The control retains P8/D8: two TP4 prefill workers on node 0 and one TP8/EP8 decode worker on node 1. The candidate changes only placement and role partitioning: three TP4 prefill workers and one TP4/EP4 decode worker. Candidate placement is P0 node 0, TP4, HTTP/bootstrap 30100/9000; P1 node 0, TP4, 30101/9001; P2 node 1, TP4, 30102/9002; D0 node 1, TP4, 30200/0 (decode does not use a bootstrap port). Each node uses eight GPUs and 64 CPUs at eight CPUs per GPU. The existing topology launcher and pair warmup enumerate placement rows and form all prefill/decode pairs dynamically; the CPU fixtures verify that behavior for three prefills and one decode.

Each proposal is a separate 16-H200, two-node Slurm allocation with a 17-minute ceiling. The allocations must run serially, not together. They consume no PBS SU, but each uses a full H200 allocation. The existing source placement and server-launch loops are generic; candidate role arguments derive TP and decode EP from each placement row. The current decode worker preflight checks Hopper and the installed HPC-Ops FP8 kernel, and real P/D warmup requests exercise the backend before benchmark traffic. The current warmup helper checks for a nonempty `choices` response but does not retain the newer semantic per-pair receipts; this is a review limit, not proof of a semantic receipt. Neither the preflight nor old topology scores prove that the pinned image supports TP4/EP4 HPC-Ops or that N60 decode KV fits. Any worker exit, kernel error, OOM, readiness timeout, or warmup failure must stop before benchmark traffic.

The extracted HPC-Ops wrapper has no explicit TP4/EP4 restriction, but it requires FP8 E4M3FN expert weights, BF16 hidden states, 128×128 block quantization for the blockwise path, gated SiLU, and global top-k IDs with contiguous expert partitioning under EP. It also states that the kernels are tuned mainly for H20 and may give limited or no speedup on H100/H200. No local source evidence establishes N60 memory headroom for a four-GPU decode worker. Log the resolved decode TP/EP, memory/KV readiness and actual kernel initialization; keep sampled VRAM distinct from KV occupancy.

There is an additional transport risk specific to this candidate. The copied NIXL patch only replaces the heterogeneous-TP preparation path. In `_prepare_payload_xfer`, a TP4 prefill to TP4 decode peer takes the equal-TP branch, which calls `_init_equal_tp_prep_handle` for source and destination pools. `_prep_equal_tp_dlist` creates one descriptor for every KV slot in every registered pointer region: for each region it computes `n = kv_data_len // kv_item_len`, builds `n` addresses with `np.arange`, then materializes and vertically stacks three `uint64` columns (address, length, device ID). For a K/V-only 94-layer rank with one pointer region per K/V layer, that is 188 regions and `188 × S` descriptors per prepared handle for `S` slots per layer, before NIXL's own registration allocations. The NumPy table alone is 24 bytes per descriptor; per-region arrays plus final `vstack` require at least another table-sized copy at peak. As illustrative bounds per rank and prepared handle, 100,000 slots imply 18.8 million descriptors and at least 0.9 GB across retained arrays and stacked table; 1,000,000 slots imply 188 million descriptors and at least 9 GB, before temporary arrays and NIXL overhead. These are formula examples, not measured H200 pool sizes.

The heterogeneous TP4→TP8 path instead records layer pointers/strides in `_init_hetero_tp_prep_handle`, and `send_kvcache_slice` builds transfer descriptors only for requested token pages. The retained 188-descriptor geometry fixture checks a prompt-sized case; it does not measure full-pool equal-TP preparation. No source artifact here gives actual H200 `kv_data_lens`, slot counts, equal-TP preparation time, or peak host memory for P12/D4. The equal-TP preparation routine has no local descriptor-count/RSS cap or per-call time deadline; the 17-minute Slurm limit is only an outer kill boundary. Because the candidate changes every P/D peer to equal TP, this potentially large setup is untested and may exceed host memory or consume the short-screen time budget. The proposal is not ready to freeze or run until a bounded assessment derives expected per-rank descriptor count and host-memory use from actual candidate pool geometry, or a separately reviewed transport design addresses equal TP. Do not modify NIXL transport for this hypothesis.

## Gates and interpretation

Before preparing proposals, `guardedprepare.py` requires reviewed job 25365 with state `LOCAL_PROTOCOL_SLA_OUTPUT_PASS`, full scored-protocol equality, passed local SLA/output/long-context gates, and the actual recorded P8/D8 DeepGEMM/HPC-Ops runtime. It also verifies the immutable source checksums and unused destination IDs. This is a preparation gate only; no submission authorization is encoded.

Before any later full N60 pair can be considered, both short screens must have zero request errors and cancellations, joint SLA fraction at least 0.90, and no output-regression case relative to the control. The P12/D4 candidate must improve short good output tokens/s by at least 1% over the fresh P8/D8 screen control. If any gate fails, close this exact P12/D4 branch; do not repeat it unchanged. If it passes, the result only supports considering a separately reviewed full-duration matched pair. The score contrast alone does not show that the early bad requests were caused by prefill capacity. Given the observed upper ceiling of roughly 1.3% full-score SLA recovery from eliminating all early bad requests, this is a bounded interaction test, not a large expected gain.

The current `review-wave10.py` validator assumes no more than two prefill roles and an eight-GPU decode role. Before any later score can be accepted, a separate reviewer must explicitly support P3/D4 and TP4/EP4, test role count and placement, reconstruct all worker arguments, verify the candidate's transport geometry and GPU UUID coverage, and exercise the scorer against CPU fixtures for both topologies. This preparation does not alter that validator or claim that a future P12 result is reviewable today.
